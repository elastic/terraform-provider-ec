## Context

See proposal.md — Why. `ec_elasticsearch_project` is a Terraform Plugin Framework resource (no SDKv2). CRUD goes through the generated serverless client in `ec/internal/gen/serverless/`, not `cloud-sdk-go`. The create, patch, and read bodies for `search_lake` are built by hand in `ec/ecresource/projectresource/elasticsearch.go` from the generated models (`ElasticsearchSearchLake` for create and read, `OptionalElasticsearchSearchLake` for patch).

The project API defines `search_lake.min_search_vcu` on `POST /api/v1/serverless/projects/elasticsearch`, `GET .../elasticsearch/{id}`, and `PATCH .../elasticsearch/{id}`: integer, `minimum: 2`, `maximum: 4992`, `nullable` on patch, absent from the GET response when unset. There is no server-side default. On patch an omitted key means "unchanged" and `null` means "unset"; `search_lake: null` as a whole resets the block, including `search_power` and `boost_window`, to defaults. The project API can apply a lower maximum to some organizations and may change the maximum over time; it enforces that limit itself, so the spec's `maximum` is not the only limit.

The provider vendors the production public bundle `specifications/generated/production/public-user-serverless-api-dereferenced.yml` of `elastic/serverless-api-specification` at the commit pinned in `ec/internal/gen/serverless/serverless-project-api.source` (`07c1cd8d` today). `x-exclude-from-documentation` on the field kept it out of that bundle until the extension was removed and the field appeared in the production bundle on 2026-11-16. Since `07c1cd8d` the production bundle has also gained `metadata.annotations` on create, read, and patch, which `make gen` would turn into a `metadata.annotations` attribute on all three project resources.

`client-config.yaml` uses default oapi-codegen settings: nullable properties become `*T` with `json:",omitempty"`, so a nil pointer is omitted and cannot encode `null`. The audit-logging change (#1104) solved the same problem with `PatchElasticsearchProjectWithBodyWithResponse` and a raw JSON body assembled by `mergeMonitoringField` in `audit.go`.

`modify_spec.sh` already rewrites generated project schemas with `jq` before `tfplugingen-framework` runs. The generator marks optional-on-create, present-on-read properties `computed_optional`; the current `search_lake` block and its two children are `computed_optional`.

## Goals / Non-Goals

**Goals:**

- One optional integer attribute, `search_lake.min_search_vcu`, whose absence in a configured block means "no floor" and is sent as JSON `null` when a floor exists.
- Generated models from the public production bundle. Hand-written code maps the field. Generated files are not edited by hand.
- Unit tests that assert the marshalled JSON of create and patch bodies, including the `null` unset path, and the read mapping. Acceptance stays a human/Buildkite step.

**Non-Goals:**

- Hand-editing the vendored spec or keeping a spec overlay in the repository.
- Turning on oapi-codegen `nullable-type`; that changes `OptionalElasticsearchSearchLake`, `OptionalLinkConfiguration`, `OptionalTrafficFilters`, `OptionalMonitoring`, and every caller.
- Exposing `metadata.annotations`. The ref bump brings the API schema in; this change keeps it out of the Terraform schema.
- Making the provider aware of organization-specific limits or of how the field is rolled out.
- Changing `search_power` or `boost_window` behaviour. They stay `computed_optional`.

## Decisions

- **Generate from the public production bundle.** Set `ref` in `serverless-project-api.source` to the first commit on `main` whose production bundle contains `search_lake.min_search_vcu`, run `scripts/update-serverless-spec.sh`, then `env -u TF_ACC make gen`. Alternative: hand-write the Go fields now and regenerate later — rejected, the next `make gen` deletes them. Alternative: pin to a pre-production bundle — rejected, `.source` records provenance for the production bundle and Renovate tracks that path.
- **Make `min_search_vcu` optional, not computed.** In `modify_spec.sh`, set `computed_optional_required` to `optional` on `elasticsearch_project.search_lake.min_search_vcu`. With `computed_optional`, a null configuration value would be planned from prior state and the floor could never be removed from Terraform: the framework cannot distinguish an explicitly null attribute from an omitted one, and for a computed attribute Terraform proposes the prior value in both cases. Optional-only means removing the line is a real plan diff to null. `search_power` and `boost_window` keep `computed_optional` so existing configurations do not change behaviour. The parent `search_lake` block also keeps `computed_optional`; a non-computed child inside it does not hide removal, because the diff is on the child.
- **Plan an omitted `search_lake` block from prior state in `Modify`.** Terraform core's proposed-new-state rule for an optional+computed object attribute with a null configuration is "keep the prior value" — except when the prior object holds a non-null value in a non-computed child (`optionalValueNotComputable` in `internal/plans/objchange`), in which case core proposes the configuration value, null. Today every `search_lake` child is computed, so an omitted block always keeps its prior value. With `min_search_vcu` optional-only, a prior state that holds a floor would make an omitted block propose null, the framework would mark the computed block "known after apply", `Patch` would skip it, `Read` would store the floor again, and the next plan would repeat — an endless in-place update, including after a practitioner deletes a block that set the floor. The audit-logging change avoided this by making `monitoring` optional-only end to end; that is not an option here because `search_power` and `boost_window` must stay computed. So `elasticsearchModelReader.Modify` sets `plan.SearchLake = useStateForUnknown(plan.SearchLake, state.SearchLake)` when the configuration `search_lake` is null and the state value is known — the existing helper already used for `credentials`, `endpoints`, and `metadata`. Plan equals prior, so there is no diff; on create the state is null and the block stays unknown. `Patch` then skips `search_lake` when the planned value equals the state value, so an omitted block still sends nothing. Alternative: a `UseStateForUnknown` plan modifier on the generated attribute via `modify_spec.sh` — functionally equivalent (an object-level modifier fires only when the whole object is unknown), but rejected because `Modify` already centralizes this logic for the resource alongside `credentials`, `endpoints`, and `metadata`, and a `Modify` case is unit-testable without a schema round-trip.
- **Leave the API's maximum to the API.** Replace the generated `int64validator.Between(2, 4992)` with `int64validator.Between(2, 2147483647)`. The API's maximum can differ between organizations and may change; a provider-side copy of it would reject values the API accepts and need a release every time the limit moves. The 2147483647 bound is not that maximum: Create and Patch convert the value to Go `int`, which is 32 bits on the released `386` and `arm` builds, so a larger value would wrap (4294967298 becomes 2) and silently send a different floor. This is a deliberate difference from `search_power` and `boost_window`, whose maxima are fixed and validated at plan time.
- **Unset with JSON null, siblings untouched.** When the prior state has a floor and the plan has `search_lake` set with `min_search_vcu` null, the patch must contain `"search_lake":{"min_search_vcu":null,...}`. The generated `*int` + `omitempty` cannot encode that, so the patch uses `PatchElasticsearchProjectWithBodyWithResponse` with a raw body. Generalize `mergeMonitoringField(body, raw)` into a helper that marshals the typed request and overrides one or more top-level keys with pre-encoded JSON (for example `mergeRawFields(body, map[string]json.RawMessage)`), so a single patch can carry both an audit null and a search-lake null. The raw `search_lake` object carries the planned `search_power` and `boost_window` when known, exactly as the typed path does, and `min_search_vcu: null`. Alternative: send `search_lake: null` — rejected, it resets the siblings. Alternative: omit the key — rejected, the API leaves the floor in place.
- **Typed path when the floor is set or never configured.** When the planned `min_search_vcu` is non-null, set `OptionalElasticsearchSearchLake.MinSearchVcu` on the generated struct. When it is null in both plan and state, leave the pointer nil so the key is omitted. The unit tests compare the marshalled bytes of raw bodies, not Go structs, as `audit_api_test.go` does. An API rejection (for example a value above the organization's maximum) is surfaced the way other failed creates and patches are: an error diagnostic with the status and body.
- **Read maps the field directly.** Add `min_search_vcu` to the `search_lake` object built in `Read`: the API value when `MinSearchVcu` is non-nil, null otherwise. No prior-state logic is needed because the attribute is not computed and there is no server-side default, so the API returns a value only when someone — Terraform or the Cloud UI — set it.
- **Keep `metadata.annotations` out of the Terraform schema.** In `modify_spec.sh`, delete the `annotations` attribute from the generated `metadata` nested attribute of all three project resources. The generated client keeps the `ProjectAnnotations` types; the hand-written metadata mapping ignores them. Alternative: expose annotations now — rejected, it is a separate feature with its own semantics (patch null handling, system vs user keys) and would ride in untested. Alternative: leave the generated attribute in place without mapping it — not viable, the generated `NewMetadataValue` constructor fails with "Missing MetadataValue Attribute Value" when `Read` omits a schema attribute, so every read of the three resources would error; the only other way to keep it is to map it as null or computed in all three `Read` paths, which is the separate feature in disguise.
- **Description and docs.** Append to the generated description: that removing the attribute unsets the floor, and a link to the public Minimum Search VCUs section of the serverless project settings page (`https://www.elastic.co/docs/deploy-manage/deploy/elastic-cloud/project-settings#minimum-search-vcus`; the fragment is the heading's rendered id). Pricing and inactivity-metering consequences stay in the public docs. Add an example under `examples/resources/ec_elasticsearch_project/with-min-search-vcu/` and a template section that explains the omitted-block and configured-block semantics. The template does not show `lifecycle { ignore_changes }`: it is standard Terraform that works on any attribute, and the page already leaves it out for audit logging configured outside Terraform.
- **Acceptance test keeps the floor tiny.** `TestAcc_ElasticsearchProject_MinSearchVCU` uses 2 and 4 so the test project pre-scales to the smallest paid step for minutes only. The Buildkite organization is not a trial organization, so no gating is needed.

## Risks / Trade-offs

- [Hand-built patch JSON drifts from the generated request struct] → The raw body starts from `json.Marshal` of the typed request and only overrides `search_lake`; the unit test locks the bytes.
- [A floor set outside Terraform is removed by the next apply of a configuration with a `search_lake` block] → Standard Terraform semantics, visible in the plan. Documented in the attribute description, the resource docs, and the changelog. Teams that manage the floor outside Terraform can opt out with standard `lifecycle { ignore_changes = [search_lake.min_search_vcu] }`, which the resource docs do not repeat.
- [`Modify` keeps the prior `search_lake` when the block is omitted, so a floor set outside Terraform is never removed by an omitted block] → Intended: an omitted block is unmanaged. To remove a floor from Terraform the configuration needs a `search_lake` block without `min_search_vcu`; the docs say so.
- [Planning an omitted block from prior state tightens Terraform's post-apply consistency check] → Today an omitted block is unknown in the plan, so any value `Read` returns after apply is accepted. With the block planned as a known prior object, a `search_lake` change made in the Cloud UI between the plan-time refresh and the apply (or an apply with `-refresh=false` on stale state) fails with "Provider produced inconsistent result after apply" instead of being refreshed silently. Low likelihood; the fix is to plan and apply again, which refreshes the block. Accepted over the perpetual-diff alternative.
- [The production bundle lags the API change] → The public PR waits for the production bundle so `.source` stays honest. The release is gated on that bundle either way.
- [Ref bump drift beyond annotations] → Task 1.1 reviews the generated diff; anything beyond `min_search_vcu` and `annotations` is reported before implementation continues.
- [API later removes `maximum` from the spec or changes `minimum`] → Removing `maximum` is a no-op for this design. A changed `minimum` would need the validator updated; the generated validator diff makes it visible on the next ref bump.
- [Acceptance needs a non-trial organization] → Buildkite's organization qualifies. The agent never sets `TF_ACC`; a human runs the named `TestAcc…` case.

## Migration Plan

No state migration. Existing projects created with this provider keep `search_lake.min_search_vcu` null after the first refresh unless a floor was set outside Terraform, in which case the refreshed state carries it and a configuration with a `search_lake` block that lacks the attribute plans its removal. Rollback is a provider downgrade; the API field is unaffected.
